## 备份导入容忍「解压后重新压缩」（86efe7c）
- 现象：导出备份 zip → 解压 → 重新压缩 → 导入报「包里没有 manifest.json」。
- 根因：zipRead 用条目名精确查找（entries.has('manifest.json')）。用户重新压缩后最常见的是外层多套一层文件夹（Finder 压缩整个文件夹 → `猫咪头像墙备份-日期/manifest.json`），另外还会带入 __MACOSX/._*（AppleDouble）、.DS_Store、`./` 前缀、反斜杠分隔符等。
- 修复：zipNorm（反斜杠→/、去 ./ 与前导 /）、zipBase、zipJunk；zipRead 存归一化名并跳过目录条目与元数据垃圾；新增 zipFind(entries, want) 三级匹配——精确 → 路径尾部（容忍外层文件夹）→ 文件名（兜底）；manifest 与原图都走 zipFind。缺 manifest 的提示里列出包内实际找到的文件名，便于用户自查。
- 测试：.workbuddy/testenv/test-zipvariant.js（node 起页面、python 造变体、真实 unzip+zip -r / ditto -c -k --sequesterRsrc 各一份）7 个变体全过（含刷新后仍在）；仓库内 test-backup.html 追加 5 项重新压缩断言（用 win.zipStore 自造嵌套/../反斜杠变体 + 缺 manifest 提示）。分组 28 项、主体格 5 项回归全过。
- 坑 1：page.evaluate 里的正则别多转义（/(\\d+)/ 在源码里是匹配字面反斜杠，应写 /(\d+)/）。
- 坑 2：Chrome 启动偶崩时经管道后 exit code 是 tail 的 0，重试循环必须按键输出文本（ALL-PASS/HAS-FAIL）判断，不能看退出码。
- 坑 3：测试里「清空 IndexedDB」不会清内存里的 photos，导入后立即读内存计数不可靠；持久化要用 reload 后读取。

## 访客页图片缓存 bug（ac5b27e）
- 用户报：重发无水印版后访客页仍显示旧水印图，F12 刷新才正常。原因：share.js 取图用了 `fetch(file, {cache:'force-cache'})` —— 缓存命中就不问服务器，文件变了也不更新；photos.json 是 no-store 所以清单是新的，造成新旧错位。
- 修复：改成 `no-cache`（每次校验，未变则 304，速度基本不变）。教训：内容会被重新发布覆盖的文件，fetch 绝不能用 force-cache；no-store 只适合小清单。
